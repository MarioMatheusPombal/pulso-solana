# Contract M1 — local MCP over the SDK

**NOT AUDITED · DEVNET DEMONSTRATION ONLY**

Status: technical contract of the implemented local MCP server. The targeted protocol version is MCP `2026-07-28`, published on 2026-07-28; the implementation must pin the MCP SDK version and verify the real negotiation with the chosen client. MCP standardizes tool calls; it does not authorize transfers by itself.

## Authority boundary

```text
MCP client (model)
  → local PULSO server, stdio
  → PulsoClient (the operator's agent signer)
  → PULSO program on Solana (vault and policy)
                          ↑
               approval UI + human authority wallet
```

The server offers the four policy/transfer tools below and `pay_receipt_challenge`, described in the final section. The operator pins in local configuration the RPC endpoint (devnet or localnet), genesis hash, program ID, public authority, agent signer, mint/vault, UI URL, requested duration and the maximum validity cap of the request. M1 defaults: requested duration of 120 s and a cap of 300 s; require duration < cap to accommodate RPC time without raising the cap. The agent key stays outside the repository and the tool arguments; the human key never enters the server, a payload, a log or a test. The model neither chooses nor replaces these values. There is no mainnet, remote HTTP MCP, OAuth, SaaS, marketplace, generic signer, `send_transaction`, `approve` or `update_policy` in the MVP.

Only funds in the vault token account controlled by the PULSO program pass through this enforcement. Other wallets, programs and external tools are not intercepted automatically. The policy belongs to the authority/agent pair and the vault accepts one mint; only the human authority can record an intent or change the policy. The server cannot create human authorization. The backend/UI stores and shows the request; its `approved` status is only a hint. The authorization is the typed `IntentAuthorization` account owned by the program on-chain. The UI must show exactly the fields used to compute the signed hash.

## Wire conventions

- JSON Schema 2020-12 for `inputSchema`/`outputSchema`; every object closes with `additionalProperties: false`. `tools/call` returns `structuredContent` conforming to `outputSchema` and a JSON copy in text `content` for compatible clients. Tool errors use `isError: true` with `{code,message}`; protocol failures remain JSON-RPC errors. `stdout` carries only MCP frames; secret-free diagnostics go to `stderr`.
- Pubkeys are base58. `approvalId` is the SHA-256 action hash v1 as 64 lowercase hex characters, not a backend ID. `amount` and `expiresAt` are **decimal strings of whole units** (base units and Unix seconds); never floats or a USDC-formatted value. `nonce` is 16 bytes as 32 lowercase hex characters. `signature` is a base58 Solana transaction signature.
- `recipientTokenAccount` is the address of the **destination SPL token account**, not a wallet address. The server checks it is an SPL account with a mint equal to the configured vault; it performs no silent ATA derivation. `amount` must be positive and fit in u64. `expiresAt` must fit in i64.
- `approvalId` is an opaque handle for the model: only the validated local copy can resolve it. The model does not supply nonce, hash, agent, authority, mint, RPC, program ID, deadline or `maxUses`.

`get_policy` queries the on-chain policy of the configured pair; absence returns `POLICY_NOT_FOUND`. Limits are base units in decimal strings. `request_transfer` calls `PulsoClient.execute()` with `maxUses=1` and the duration requested by the operator; an autonomous success returns with a signature. If the simulation returns `HUMAN_INTENT_REQUIRED` or `RECIPIENT_NOT_ALLOWED`, it persists the `PendingApproval` before returning `pending` with the approval URL and the exact public `payload`. That payload is data for inspection, not an argument accepted by `execute_approved`. There is no long polling in this tool. If the URL is not configured or the backend rejects the request, it fails without promising a usable approval. A retry of `request_transfer` **may be a new transfer**: the autonomous SDK uses a zero nonce and offers no request idempotency key. The client must not repeat after an ambiguous response without checking the chain; do not promise exactly-once on this path.

`get_approval_status` queries the chain first. `approved` requires a valid, unconsumed intent; `used`, `expired` or `revoked` come from the account. Without an intent, `denied` is only the backend status for that request; it never means on-chain proof. With the backend reachable and still pending, it returns `pending`; if the backend is unavailable, it returns `BACKEND_UNAVAILABLE`. An RPC error or a malformed account is a fail-closed error, not `pending` or `approved`. `execute_approved` receives only `approvalId`, retrieves the exact local intent, verifies the chain and calls `PulsoClient.executeApproved(pending)`. The program recomputes the hash and consumes one use atomically with the transfer. A retry after success or an ambiguous response must check the signature/state; do not repeat the transfer automatically. The program rejects replay.

Stable errors: `INVALID_ARGUMENT`, `POLICY_NOT_FOUND`, `POLICY_DISABLED`, `AGENT_REVOKED`, `RECIPIENT_INVALID`, `APPROVAL_NOT_FOUND`, `APPROVAL_CONTEXT_MISMATCH`, `APPROVAL_DENIED`, `APPROVAL_NOT_ON_CHAIN`, `INTENT_MISMATCH`, `INTENT_EXPIRED`, `INTENT_ALREADY_USED`, `INTENT_REVOKED`, `RPC_UNAVAILABLE`, `BACKEND_UNAVAILABLE`, `STATE_UNAVAILABLE`, plus the program's `PULSO_00N` codes where applicable. Messages do not include private keys, configuration payloads or raw RPC logs. Chain failures prevail over backend hints.

## Persistence and validation after restart

The process writes each pending request to a private local file, outside the repo, with an atomic write and restricted permissions. Secret-free record: `approvalId`, `reason`, `approvalUrl`, `requestedAt` (Unix seconds obtained from the on-chain Clock before the attempt), the configured requested duration and validity cap, identifier/fingerprint of the configured RPC endpoint (no credentialed URL), genesis hash, program ID, policy/vault, authority, agent, mint, instruction `execute_transfer`, amount, recipient token account, nonce, `expiresAt`, `maxUses=1` and action hash. Do not depend on the UI's in-memory queue: `app/lib/store.ts` loses state on restart. If the record cannot be written or recovered, return `STATE_UNAVAILABLE` and never accept `execute_approved` for an `approvalId` coming only from the model or the backend.

On load and before each status/execution: validate format and limits; require equality with the local configuration, including endpoint/genesis (localnet can restart on the same URL), policy PDA and vault/mint; recompute the action hash v1 of the persisted fields and compare it with `approvalId`; require `expiresAt > requestedAt`, `expiresAt - requestedAt <=` the cap pinned by the operator and `maxUses=1`. On creation, reject the pending request if the SDK computes a deadline outside that range; `PulsoClient` today has a fallback to the local clock, which the MCP server must not accept as proof of chain time. Check the typed policy and vault accounts, their owners/discriminators where applicable, `enabled`, `agent_revoked`, authority, agent and mint. Fetch the intent PDA derived from authority/hash and **decode the typed account owned by the program**, checking discriminator, authority, agent, action hash, `expires_at`, `max_uses`, `used_count < max_uses`, `revoked=false`, and `now <= expires_at` with the chain clock. Do not accept the local clock as a substitute if the RPC fails. The exact hash also binds program ID, instruction, mint, amount, recipient and nonce; fields the account does not store are checked by recomputation. Execution still depends on the program's definitive validation, including the per-transaction cap and the daily limit.

An intent from another agent/authority, another network/genesis, expired, spent, revoked or with any divergence is rejected. Do not rebuild a request from the backend or an `approvalId` alone: the on-chain account holds the hash and metadata, not the full payload or the nonce. Local persistence grants no authority; it only preserves the bytes of the requested action.

## `pay_receipt_challenge`

**NOT AUDITED · DEVNET DEMONSTRATION ONLY.** Pays a `pulso-receipt-v1` 402 challenge ([AUTHORITY_RECEIPT_SPEC.md](AUTHORITY_RECEIPT_SPEC.md), sections 7 and 11) that the client has already read. Strict input: `{"scheme":"pulso-receipt-v1","programId":string,"recipient":string,"mint":string,"minAmount":"^[1-9][0-9]*$","nonce":"^[0-9a-f]{32}$","expiresAt":integer,"cluster"?:string}`; no URL, no separate amount field. It reuses the `request_transfer` path with `amount = minAmount`, `recipientTokenAccount = recipient` and the challenge nonce (on the approved path the nonce enters the action hash). Outputs: `{"status":"executed","signature":string,"challengeNonce":string}` (the client re-presents it to the receiver with `X-PULSO-Receipt` and `X-PULSO-Challenge`) or the same `pending` as `request_transfer`, resumed only by `execute_approved`; the pending approval is never valid beyond the challenge's `expiresAt` (the intent expires on-chain 5 s earlier, and a challenge less than 5 s from expiry is refused with `CHALLENGE_EXPIRED`). New errors: `CHALLENGE_INVALID` (malformed scheme, nonce, `minAmount` or `expiresAt`), `CHALLENGE_CONTEXT_MISMATCH` (`programId` or `mint` differ from the configuration), `CHALLENGE_EXPIRED` (on-chain clock). It does not fetch a URL, does not read the resource, does not decide what to buy or how much to pay, and offers no shortcut to reuse a receipt; pending does not authorize another tool.
